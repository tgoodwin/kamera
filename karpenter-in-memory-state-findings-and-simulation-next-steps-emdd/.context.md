## Context
We observed a regression where a Pod + NodePool example used to converge in ~31 steps, but now converges in ~10 when running:

```bash
go run . --inputs inputs.json --depth 50
```

This note summarizes what Karpenter source code reveals about why this can happen, and why it is not just an "input pending reconciles" problem.

## Key Finding
Karpenter controllers are not purely stateless functions over Kubernetes object snapshots.
They rely on controller-local in-memory state that must be hydrated by reconcile activity.

In particular, `state.Cluster` stores a large amount of derived runtime state and is consulted by provisioning and other controllers.

## Evidence in Karpenter Source
### 1. `state.Cluster` is a mutable, process-local cache
`pkg/controllers/state/cluster.go` defines `Cluster` with in-memory maps such as:
- `nodes`
- `bindings`
- `nodeNameToProviderID`
- `nodeClaimNameToProviderID`
- `nodePoolResources`
- `NodePoolState`

This is created in-process by `NewCluster(...)` and not reconstructed from a single object read at use time.

### 2. Provisioning is gated on internal state sync
In `pkg/controllers/provisioning/provisioner.go`, `Provisioner.Reconcile()` checks:
- `if !p.cluster.Synced(ctx) { requeue }`

`Cluster.Synced(ctx)` (in `cluster.go`) validates internal state against API-server lists before allowing scheduling to proceed.

So even if input objects are present, the provisioner can intentionally delay until internal state is hydrated.

### 3. "state.*" informer controllers are state-shaping controllers
Karpenter registers dedicated state informers:
- `state.pod`
- `state.node`
- `state.nodeclaim`
- `state.nodepool`

(see `pkg/controllers/controllers.go`)

These controllers update in-memory state via methods like:
- `cluster.UpdatePod(...)`
- `cluster.UpdateNode(...)`
- `cluster.UpdateNodeClaim(...)`
- `cluster.MarkUnconsolidated()`

Not all of these produce Kubernetes object writes, but they still change behavior of subsequent reconciles.

### 4. `state.nodepool` has behavioral effect even without object writes
`pkg/controllers/state/informer/nodepool.go` mainly calls:
- `cluster.MarkUnconsolidated()`

This does not patch objects, but it mutates internal consolidation state used by disruption/provisioning logic.

### 5. Additional in-memory state exists beyond `Cluster`
Karpenter also keeps `nodepoolhealth.State` as an in-process rolling health tracker (`pkg/state/nodepoolhealth/tracker.go`).
`nodepool.registrationhealth` and `nodeclaim.lifecycle` use this state to evaluate/update `NodeRegistrationHealthy` behavior.

This is another example of behavior depending on process-local memory, not just object snapshots.

## Why 31 Steps Can Collapse to ~10
A shorter run can occur when startup/materialization semantics are under-modeled:
- Pod creation may trigger provisioner-related controllers.
- But if startup-enqueued state informers (or equivalent dependency-triggered reconciles) do not run sufficiently, internal caches/history are not hydrated.
- Provisioning and related controllers then take early-exit/requeue paths, producing a much shorter explored trace.

So the regression is consistent with missing semantic unfolding of controller-local state materialization, not merely a wrong user input.

## Implication for Kamera Model
The important modeling distinction is:
- Not: users should specify pending reconciles in initial input state.
- Instead: simulation semantics should compute reconcile queues from actions/subscriptions and include startup/watch hydration behavior so controller-local state is materialized as in real controller-runtime systems.

Practical harness interpretation:
1. Treat CREATE/UPDATE/DELETE actions as queue seeds via watch subscriptions.
2. Include initial informer/bootstrap enqueue semantics for already-existing objects.
3. Allow non-object-writing reconciles to matter when they mutate modeled controller-local state.
4. Keep initial input focused on object state; derive pending reconciles through simulation semantics.

## CREATE-Event Modeling Workaround
### Idea
As a workaround, model existing startup objects as synthetic CREATE events so watchers enqueue reconciles without users specifying pending reconciles.

### Where it can help
- It can bootstrap `state.*` informer controllers from `environmentState`.
- It can often recover the longer "materialization first, then provisioning" trace shape.
- It keeps user-facing inputs simple (objects only, no explicit pending queue).

### Suggested variant
Use two phases:
1. Startup bootstrap phase: for each object in initial state, synthesize a CREATE event; route through normal subscription/event-filter logic; execute resulting queue to fixed point (or bounded depth).
2. User action phase: apply the user action (for example, Pod CREATE) and continue normal event-driven simulation.

### Constraints and caveats
CREATE-only modeling is useful but not equivalent to full controller-runtime semantics:
- Some controllers depend on UPDATE semantics (generation/status transitions, predicate behavior).
- DELETE-triggered maintenance is not represented by CREATE-only bootstrap.
- Time/requeue-driven behavior is separate from watch-event behavior.
- Synthetic CREATE for pre-existing objects may not mirror real startup ordering/interleavings.
- It may over-approximate or under-approximate paths depending on predicates.

### Practical recommendation
Treat startup synthetic CREATE as a configurable bootstrap policy, not the entire simulation model. It is a bridge away from `initialDependentControllers`, but long-term correctness still needs UPDATE/DELETE/requeue semantics and controller-local state transitions.

## Bottom Line
`initialDependentControllers` worked as a tactical patch because it approximated missing startup/materialization behavior.

A stronger direction is to:
- derive pending reconciles via simulation semantics,
- include startup bootstrap behavior, and
- model relevant controller-local state transitions.

A synthetic CREATE bootstrap mode can be an effective near-term workaround while moving toward that full model.

## Action Items / Next Steps
1. Add a configurable startup bootstrap policy that can synthesize CREATE events for all pre-existing objects in `environmentState`.
2. Route bootstrap-generated events through the same watcher/subscription + predicate pipeline used for runtime events.
3. Add deterministic tests for Karpenter-like flows that verify expected path length/shape (materialization-first vs early requeue).
4. Extend semantics beyond CREATE: explicitly model UPDATE/DELETE-triggered enqueues and verify controller predicate handling.
5. Model non-object-writing reconciles as state-affecting transitions when they mutate controller-local state.
6. Audit and reduce reliance on manual `initialDependentControllers` in favor of derived queue semantics.
7. Document known caveats of synthetic CREATE bootstrap and define acceptance criteria for “full semantics parity” milestones.
