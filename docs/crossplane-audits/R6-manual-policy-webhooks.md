# R-6: Manual update policy webhooks / defaulting

**Status:** ✅ AUDITED — no admission, defaulting, or conversion webhook in v2.2.0 touches the XR's `compositionRef` / `compositionRevisionRef` before they reach `APIRevisionFetcher.Fetch`.

**Threat addressed:** [CC-8](../upstream-updates/AUDIT-threats-to-validity.md#cc-8-manual-update-policy-semantics--what-does-cr-actually-do-here), [F1-T1, F1-A4](../upstream-updates/AUDIT-threats-to-validity.md#f1-7220--manual-update-policy-wrong-revision)

## Question

Does Crossplane v2.2.0 ship any admission webhook, mutating webhook, defaulting webhook, or conversion webhook on XR objects that would auto-correct mismatched `compositionRef` / `compositionRevisionRef` fields before they reach `APIRevisionFetcher.Fetch`? If yes, the F1 trace would not reproduce on a real cluster.

## Research method

1. Grepped the Crossplane v2.2.0 source for `webhook`, `MutatingWebhook`, `ValidatingWebhook`, `defaulter`.
2. Inspected `internal/initializer/webhook_configurations.go` (the install-time webhook installer).
3. Inspected `internal/webhook/` for handler implementations.
4. Listed `cluster/webhookconfigurations/*.yaml` (the shipped configurations).
5. Inspected the XRD CRD generator (`internal/xcrd/schemas.go`) for OpenAPI default values on the relevant fields.
6. Re-read `internal/controller/apiextensions/composite/api.go:157-168` to confirm the path that sees the mismatched refs.

## Findings

### Only one webhook ships in v2.2.0

`cluster/webhookconfigurations/` contains exactly one webhook YAML:

- `usage.yaml` — `ValidatingWebhookConfiguration` named `crossplane-no-usages` (the protection webhook). Selector: `objectSelector.matchLabels.crossplane.io/in-use=true`. Operation: `DELETE`. Handler: `internal/webhook/protection/usage/handler.go`.

`internal/webhook/` contains only `protection/usage/`. There is **no** webhook directory for `apiextensions`, no XR mutating webhook, and no conversion webhook.

`internal/initializer/webhook_configurations.go:67-141` only loads YAMLs from disk and installs whatever is found — there is no programmatic XR webhook registration.

### XRD-generated CRD has no defaults on the relevant fields

`internal/xcrd/schemas.go:78-150` generates the OpenAPI schema for `spec.crossplane.compositionRef`, `spec.crossplane.compositionRevisionRef`, and `spec.crossplane.compositionUpdatePolicy`. Of these:

- `compositionRef` (lines 80-86): no `Default` set.
- `compositionRevisionRef` (lines 100-106): **no `Default` set** — the field is purely user-controlled.
- `compositionUpdatePolicy` (lines 120-132): has a `Default` only if the XRD author explicitly set `spec.defaultCompositionUpdatePolicy`. The XRD-level default propagates to the CRD-level default; otherwise no default.

There is no conditional defaulter that would re-derive `compositionRevisionRef` from `compositionRef`.

### The reconciler path itself does not re-derive

`internal/controller/apiextensions/composite/api.go:157-168`:

```go
func (f *APIRevisionFetcher) Fetch(ctx context.Context, cr resource.Composite) (*v1.CompositionRevision, error) {
    current := cr.GetCompositionRevisionReference()
    pol := cr.GetCompositionUpdatePolicy()

    // We've already selected a revision, and our update policy is manual.
    // Just fetch and return the selected revision.
    if current != nil && pol != nil && *pol == xpv1.UpdateManual {
        rev := &v1.CompositionRevision{}
        err := f.client.Get(ctx, types.NamespacedName{Name: current.Name}, rev)

        return rev, errors.Wrap(err, errGetCompositionRevision)
    }
    // ... Automatic / unset path ...
}
```

When `policy == Manual` and `compositionRevisionRef != nil`, the fetcher does a bare `Get(currentRevision.Name)` with **no validation** that the revision belongs to the Composition referenced by `compositionRef`. This is exactly the F1 mechanism.

## Threat resolution

| Threat | Resolution |
|---|---|
| **CC-8 / F1-T1**: defaulting webhook auto-syncs `compositionRevisionRef` to a valid revision under `compositionRef` | RESOLVED — no such webhook ships in v2.2.0. |
| **F1-A4**: no mutating webhook in production rewrites `compositionRevisionRef` to match `compositionRef` automatically | RESOLVED — no XR-targeted mutating webhook exists. |
| Conversion webhook on XR | RESOLVED — XRDs generate plain CRDs; no `spec.conversion` is generated by `internal/xcrd/`. |

## What this means for F1 posting

CC-8 / F1-T1 is no longer a blocker for posting #7220 from the simulation alone. The bug mechanism lives in plain controller code with no admission-layer interception. R-11 (real-cluster reproduction) is still the strongest possible evidence, but the webhook fidelity threat is closed.

## What's NOT addressed

- **Third-party operators / providers** could install their own mutating webhook on `apiextensions.crossplane.io` group resources. This is out of scope; Crossplane core does not ship one.
- **Versioned XRDs with custom CEL validation** could in principle reject mismatched refs at admission, but `internal/xcrd/schemas.go` does not emit any CEL rules linking `compositionRef` to `compositionRevisionRef`. A user-authored XRD could add such a rule, but that is a user-defined gate, not a v2.2.0 default behavior.
- **R-11** (real-cluster reproduction) is still the strongest possible audit but is not blocked by anything found here.
