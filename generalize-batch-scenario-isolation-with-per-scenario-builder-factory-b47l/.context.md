Problem
Batch runs can execute scenarios concurrently, but some harnesses need mutable setup state (e.g., singleton-style shims, shared adapters, cached controller deps). Today, ParallelRunner relies on ExplorerBuilder.Fork(), which clones builder maps but keeps constructor closures. If those closures capture mutable state, in-process parallel scenarios can contaminate each other.

Observed in Karpenter
Karpenter's harness used closure-captured switcher/cluster/provisioner state. Under concurrent in-process batch runs, this caused cross-scenario frame-manager contamination and intermittent "frame not found" failures. We mitigated this by serializing in-process batch for Karpenter, but that is intentionally a stop-gap.

Goal
Implement a generalizable isolation model for batch runs so harnesses can safely include mutable runtime wiring while still allowing parallel scenario execution.

Scope
- Add a batch execution path that can build a fresh, scenario-scoped ExplorerBuilder per scenario (builder factory), instead of requiring Fork() from a shared builder instance.
- Keep existing behavior available for harnesses that are already fork-safe.
- Migrate Karpenter to use the generalized mechanism, removing reliance on serial in-process execution as the long-term fix.
- Document guidance for harness authors on when to use fork-shared mode vs factory-isolated mode.

Non-goals
- Do not make each harness invent its own isolation workaround.
- Do not hardcode Karpenter-specific logic into generic explore/tracecheck internals.
