K13 Divergence Summary: Multiple HealthRecords race on resource request status
=================================================================================

Hypothesis: When multiple HealthRecords exist for the same resource request,
the HealthRecordController's List + filter + aggregate + write pattern produces
ordering-dependent healthStatus in the resource request.

Result: CONFIRMED

Two HealthRecords ("healthcheck-1" state=healthy, "healthcheck-2" state=degraded)
for the same EasyApp resource request. With controller ordering permutation and
staleness intervals on EasyApp reads, the EasyApp status diverges into 2 variants:

  EasyApp hash 967603d4: 13/20 trials (65%) -- majority
  EasyApp hash 8c32a871:  7/20 trials (35%) -- minority

Root cause: The HealthRecordController's updateResourceStatus() method does:
  1. List ALL HealthRecords (not filtered server-side)
  2. Filter by resourceRef name/namespace in Go code
  3. Compute aggregate state using priority (unhealthy < degraded < unknown < healthy < ready)
  4. Write the full healthStatus map to the resource request status

When two HealthRecord reconciles race with staleness, the second reconcile may
see a stale version of the EasyApp that doesn't include the first reconcile's
healthStatus update. The second write then overwrites the first's healthStatus
with a potentially different aggregate state (e.g., if it sees a different set
of HealthRecords due to List staleness).

Scenario: k13_multiple-healthrecords-race.json
Perturbation: permuteControllers + stalenessIntervals on EasyApp reads
Trials: 20
EasyApp distinct states: 2 (65% / 35% split)
Total distinct final states: 3 (PromiseRevision noise adds a third)
