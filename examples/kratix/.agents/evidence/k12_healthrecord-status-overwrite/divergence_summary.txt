K12 Divergence Summary: HealthRecord + DynamicResourceRequest status overwrite
=================================================================================

Hypothesis: HealthRecordController and DynamicResourceRequestController race on
the EasyApp resource request status subresource, producing ordering-dependent
final states.

Result: NEGATIVE for EasyApp divergence

The EasyApp status converges to the same hash across all trials in both
ordering-permutation and staleness-interval runs. Although both controllers
write to the EasyApp status (HealthRecordController writes status.healthStatus,
DRRController writes status conditions), the writes modify disjoint fields
and the replay system applies them sequentially, so the final state is the
same regardless of ordering.

Key observation: the status subresource updates modify different subfields
(healthStatus vs conditions), so even in a real Kubernetes cluster, the
conflict would only manifest if both controllers read the EasyApp at the
same instant (before either writes), then both write. The replay model
doesn't capture this particular form of TOCTOU.

The only divergence observed was in PromiseRevision status (a known Promise
lifecycle artifact, not related to the HealthRecord interaction).

Trials: 20 (10 reference, 10 with staleness intervals)
EasyApp distinct hashes: 1 (consistent across all trials)
PromiseRevision distinct hashes: 2 (known noise)
