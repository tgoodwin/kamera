## Goal
Audit harness structure across `examples/knative`, `examples/karpenter`, `examples/kratix`, and `examples/crossplane` to assess structural similarities and identify where behavior is primarily driven by Kamera semantics + external inputs versus custom per-harness code.

## Why
We need a clear map of where divergence in behavior is coming from:
- Common Kamera runtime semantics
- Input/state configuration differences
- Custom harness-specific adapter logic ("harness hacking")

## Key Questions
1. What are the shared harness components and extension points across all four examples?
2. Which behaviors are controlled by Kamera framework semantics (eventing, queueing, simulation loops, etc.)?
3. Which behaviors are controlled by external inputs (`inputs.json`, scenario setup, config toggles)?
4. Which behaviors depend on custom harness code and project-specific glue?
5. Where are customizations unavoidable versus accidental/legacy?
6. What standardization opportunities exist to reduce harness-specific drift?

## Scope
- Compare structure and execution flow for:
  - `examples/knative`
  - `examples/karpenter`
  - `examples/kratix`
  - `examples/crossplane`
- Identify and classify per-harness logic into:
  - framework-driven
  - input-driven
  - harness-custom
- Produce recommendations to reduce custom logic where feasible.

## Deliverables
1. A comparison matrix of the four harnesses:
   - bootstrapping
   - controller wiring
   - watch/event mapping
   - input loading
   - scenario/action injection
   - custom adapters/shims
2. A behavior-attribution breakdown:
   - what is driven by Kamera core
   - what is driven by input data
   - what is driven by harness-specific code
3. A prioritized list of refactor candidates to increase shared structure.
4. Proposed acceptance checks to ensure future harnesses stay within the common pattern.

## Action Items / Next Steps
1. Inventory harness entrypoints and wiring paths for all four examples.
2. Build a side-by-side structural diff focused on lifecycle stages (init, bootstrap, event flow, reconcile scheduling, termination).
3. Trace 1-2 representative behavior differences per harness back to their root driver (core semantics vs inputs vs custom code).
4. Identify duplicated custom logic and propose extraction points into shared utilities or framework interfaces.
5. Define a minimal "standard harness contract" and list current gaps per example.
6. Recommend short-term cleanup tasks and longer-term architectural changes.
7. Capture findings in a single report with explicit evidence links to files/functions.

## Acceptance Criteria
- All four harnesses are analyzed with consistent comparison dimensions.
- Every major behavior class has explicit attribution (Kamera, input, or harness custom code).
- Report includes at least 5 concrete refactor/standardization opportunities with impact/risk notes.
- Proposed contract is specific enough to guide implementation of future harnesses.
